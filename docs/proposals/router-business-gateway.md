# 路由业务网关集成提案

状态：草案，关联 [#12](https://github.com/imneov/modelsphere-console/issues/12)。首批范围为计费与循环检测；本提案尚不代表行为定义、交接或集成验收完成。

## Background

- 负责人：liufeng；代码交接协作：qiliguo。

- 会议所指路由组件及接入位置仍需核对。代码来源、版本及运行资料在原 Issue 指向的私有补充资料中确认，本文件不复制私有资料。
- LF 已确定交付路径：所有代码先提交至 `imneov/modelsphere-console`，后期统一提交 PR。本阶段使用任务分支，不提交上游 PR。

## Proposal

先确认计费身份、用量与检测动作在现有请求链路中的位置，再接入已有网关能力。

| 事项 | 提案 |
| --- | --- |
| 认证入口 | 保留现有 Key 校验、过期检查和模型授权语义，按最终接入位置确定适配 |
| 计费身份 | 从已验证的调用者映射到账务主体；不能默认用共享后端凭据或 Key 创建者作为费用归属 |
| 用量 | 依据约定协议的实际 usage，区分输入、输出、缓存和中断场景 |
| 计价和账目 | 复用交接确认的计费能力，明确统计或扣费范围以及权威记录所在服务 |
| 循环检测 | 根据确认的业务含义确定检测层、正反例、阈值和动作 |
| 交付 | 在 fork 任务分支提交、推送实现与验证记录，PR 留到后续统一提交阶段 |

## User experience

### Use cases

1. 平台维护者完成已有网关代码、版本、配置与运行说明的交接，按约定接入路由。
2. 调用者使用有效 Key 调用模型，响应正常返回，用量和费用归属可核对。
3. 对确定的循环场景，系统执行约定的检测和处理动作，正常请求不受影响。
4. 维护者能够关联请求结果、检测结果与计费记录，确认实际行为。

### What the user sees

本草案尚未选择新增页面、API、配置项或错误码。需要先明确：

| 待确认项 | 对结果的影响 |
| --- | --- |
| 费用统计还是包含实际扣费 | 决定是否引入余额、扣费和账务写入路径 |
| 用户、Key、模型等费用归属及单位 | 决定数据映射和与 #8 的查询口径 |
| 循环的含义与处理动作 | 决定是处理生成内容、转发链路，还是其他业务对象 |
| 目标组件及约定环境 | 决定适配位置、请求路径及实际验收入口 |

## Design

### Overview

现有 Console 的公开实现：

```text
程序 ──用户 Key──> Console /v1
                     │ 校验 Key、过期和模型范围
                     │ 查找模型后端、替换凭据
                     ▼
                 现有推理网关 ──> 推理引擎
```

| 现有模块 | 已核实职责 | 集成边界 |
| --- | --- | --- |
| [router](../../internal/router/router.go) | 校验 Key，选择模型后端，流式转发 | 计费上下文必须保留已经校验的调用身份 |
| [Key 数据](../../internal/router/key.go) | Key ID、模型范围、创建者和过期时间 | 当前结构没有独立的计费账户字段 |
| [Key 管理](../../internal/router/keys_http.go) | 创建和删除 Key | `CreatedBy` 是创建行为的记录，不等于已经确认的费用归属 |
| [Key 存储](../../internal/router/store.go) | 在 Kubernetes Secret 保存 Key，缓存读取 | 不应直接把高频用量与账目写进该 Secret |
| [后端解析](../../internal/gateway/gateway.go) | 从站点配置、路由 ConfigMap 和 Secret 解析入口及凭据 | 同一后端的共享凭据不足以区分不同调用者 |
| [路由指标](../../internal/router/metrics.go) | 请求、拒绝和最近使用指标 | 请求计数不等于 token 用量或金额账目 |

拟议处理顺序：

```text
确认交接与目标组件
        │
        ▼
明确调用身份 → 用量来源 → 计费主体/价格/账目
        │
        ▼
确认循环对象 → 检测位置 → 触发动作 → 计费处理
        │
        ▼
fork 分支实现 → 实际链路验证 → 记录验收 → 后续统一 PR
```

### API and configuration

- 当前外部调用入口为 `/v1/*`，现有 Key 管理入口为 `/api/router/apikeys`。
- 若已有网关放在 Console 前面，须确认两层 Key 如何衔接以及 Console 是否仍可识别实际调用者。
- 若放在 Console 后面，须确认共享后端凭据下如何传递并验证计费主体。
- 若把能力适配进 Console，则必须明确允许复用的交接模块、配置和依赖边界。
- 在目标与身份契约确定前，不增加占位 API、配置开关、账务表或检测规则。

### Security

- 身份使用已验证的数据，客户端自行填写的身份字段不能直接作为费用归属。
- 现有凭据改写行为需与计费服务鉴权对应，不能转发用户密钥来代替身份映射。
- 日志和验证材料使用请求标识、Key ID 和配置来源，不记录密钥明文。
- 私有交接信息保留在授权的私有资料中。

### Compatibility and upgrade

- 保留现有 Key 生命周期、模型范围及流式转发行为；确需改变时在方案中明确迁移和验收方式。
- 数据迁移、已有 Key 的费用归属、重复投递和中断后的处理依据最终交接方案验证。
- 配置、API 或跨组件行为的变化先更新本提案，再实施。

### 拟议验收场景

| 场景 | 操作 | 可观察结果与完成判据 |
| --- | --- | --- |
| 首次接入 | 在约定环境配置接入位置，用真实模型完成一次请求 | 请求抵达指定组件，模型响应和身份映射正确，可追踪到真实用量记录 |
| 正常计费 | 记录请求前状态，分别发首批约定的流式和非流式请求，再核对 usage、价格与账目 | 输入、输出、缓存口径、费用归属与金额可对账；若包含扣费，还需核对余额变化 |
| 权限边界 | 使用过期、撤销、模型范围不符的 Key 请求 | 保持约定的认证授权行为，并按确认规则处理是否产生账目 |
| 循环正例与反例 | 使用确认的应命中样例及正常样例 | 正例触发约定动作，反例通过；请求结果、下游取消和计费处理符合约定 |
| 中断与缺少 usage | 使用已确认的中断场景 | 记录实际可得用量及约定估算/拒绝规则，不把输出分片数量默认为精确 token 数 |
| 依赖恢复 | 在允许演练的环境按约定控制点中断并恢复依赖 | 核对请求、消息、用量和账目恢复结果；不能仅凭服务恢复判定结算成功 |
